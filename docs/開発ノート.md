# Tiger QuickLook 開発ノート — 苦労した点と工夫した点

Mac OS X 10.4 Tiger の実機（iBook G4 / 1.2GHz / 1.25GB RAM）で動く、
軽量な Quick Look 代替を作ったときの記録。Quick Look は Leopard (10.5)
からの機能で、Tiger には存在しない。「Finder でファイルを選んで Space、
プレビューが出る」という Leopard 以降の操作感を、Tiger の上で再現するのが
ゴール。

対応形式は **JPG / PNG / PDF / TXT の 4 つだけ**に絞った。何でも表示しよう
とすると重くなり、非力な実機で常用に耐えなくなるため、意図的に深追いしない。

---

## 1. 「重くしない」を最優先に設計した

実機は 2005 年の iBook G4。QuickLook もどきのせいでマシン全体がもたつく
なら本末転倒なので、削る判断を優先した。

- **画像**：フル解像度でデコードしてから縮小する、ではなく、
  `CGImageSourceCreateThumbnailAtIndex` に
  `kCGImageSourceThumbnailMaxPixelSize` を渡して**最初から縮小デコード**する。
  10MB の写真でも実際に展開されるのはプレビュー寸法ぶんだけ。
- **PDF**：PDFKit は Tiger に無いので使えない（そもそも重い）。
  `CGPDFDocumentCreateWithURL` → 1 ページ目だけを `CGContextDrawPDFPage` で
  その場描画する。`CGPDFDocumentCreateWithURL` はページを遅延パースするので、
  **200 ページの PDF でも開くのは一瞬**。効いてくるのは「1 ページ目の中身の
  複雑さ」だけで、ファイルサイズではない。
- **TXT**：ファイル全体を読まず、`NSFileHandle` で**先頭 64KB だけ**読んで
  編集不可の `NSTextView` に流す。巨大なログでも頭打ち。
- **先読みしない・キャッシュしない・ウィンドウは使い捨て**。選択された
  1 ファイルだけをその場で生成し、閉じたら（単発モードでは）プロセスごと終了。

実測：1 ページに 2550×3300 のスキャン画像を貼った 5.4MB の PDF で、開くのに
ひと呼吸、ウィンドウのドラッグリサイズの追従が少しもたつく程度。CPU は
瞬間 100%、通常 60%。この体感なら、オフスクリーンのビットマップキャッシュ
などの作り込みは**やらない**と判断した。

---

## 2. 「Space キー一発」をどう実現するか

いちばん悩んだところ。要件は「Leopard と同じく、修飾キーなしの Space
一発でプレビュー」。

- **Services メニュー案は不成立**。Tiger の Finder は選択中のファイルを
  Services のペーストボードに載せないので、Services 項目は常にグレーアウト
  （10.5 で改善された挙動）。ショートカットを割り当てても発火しない。
- **`⌘Y` などの修飾キー付き**なら `RegisterEventHotKey`（Carbon）で
  実装でき、システム設定も不要だが、「キーが遠い」ため不採用。
- 結局、**修飾なし単キーを条件付きで横取りする手段は `CGEventTap` しかない**。
  そして Tiger の `CGEventTap` は、システム環境設定「ユニバーサルアクセス」の
  **「補助装置にアクセスできるようにする」を有効化**しないと生成できない。
  ここは避けられないので、一度きりの設定として配布ドキュメントで強く周知する
  方針にした。

構成：Dock アイコンを持たない常駐エージェント（`LSUIElement`）が
`CGEventTap`（`kCGSessionEventTap`, head-insert）で Space のキーダウンを監視。
「Finder が最前面」かつ「プレビュー非表示」のときだけイベントを飲み込み、
`NSAppleScript` で Finder に選択項目を尋ねてプレビューを出す。もう一度 Space、
または Esc で閉じる。Finder 以外が最前面のときは Space をそのまま素通しする。

## 3. いちばん厄介だったバグ：Terminal で Space が全角になる

エージェントを動かした状態だと、**Terminal で Space を打つと半角スペースでは
なく全角スペース（U+3000）が入る**という現象に遭遇した。TextEdit では正常。

原因は、**アクティブなイベントタップをキーイベントが通過すると、WindowServer
がそのイベントを「現在の入力ソース」で確定してしまう**こと。日本語入力が
有効だと Space が全角に変換され、`[event characters]` を直接読むタイプの
アプリ（Terminal など）がその全角を受け取ってしまう。TextEdit はフルの
テキスト入力経路を通るので影響が出なかった。

対策：**タップを常時有効にしない**。「Finder が最前面、またはプレビュー
表示中」のときだけ `CGEventTapEnable` する。ただし Tiger には最前面アプリの
変化を知らせる通知が無い（`NSWorkspaceDidActivateApplicationNotification`
は 10.6 以降）。仕方なく **0.3 秒ごとの `NSTimer` ポーリング**で前面アプリを
見て有効／無効を切り替えている。副作用として、Finder に切り替えた直後の
最大 0.3 秒だけ Space が効かないが、ファイルを選ぶ動作で十分に間が空くので
実用上は気にならない。

## 4. Tiger SDK / GCC 4.0 の地雷

現行の Xcode / Clang の常識が通じない。踏んだものを列挙する。

- **`CGFloat` が存在しない**。64bit 移行（Leopard 以降）で入った型なので、
  Tiger では素直に `float` を使う。
- **`CGPDFPageRef` は親の `CGPDFDocumentRef` を延命してくれない**。
  ページだけ retain して document を release すると、後からページに
  アクセスした瞬間に解放済みメモリを踏んで `EXC_BAD_ACCESS`。document ごと
  保持し、描画のたびに `CGPDFDocumentGetPage` で取り直す。
- **`kCGEventTapOptionDefault` が 10.4 のヘッダに無い**。`0` を直接渡す。
- **`NSWorkspaceDidActivateApplicationNotification` は 10.6 以降**（上記 3）。
- **`@"日本語"` リテラルが文字化けする**。GCC 4.0 は `@"..."` 内の非 ASCII を
  実行時エンコーディングで解釈するため、メニューやダイアログが化ける。
  ユーザーに見える文字列は `[NSString stringWithUTF8String:]` を通して
  UTF-8 として明示デコードする。
- **`xcodebuild` がこの実機では壊れている**（`DevToolsSupport.framework` が
  見つからない）。`gcc -isysroot /Developer/SDKs/MacOSX10.4u.sdk ...` で
  直接コンパイル・リンクし、`.app` バンドルはシェルスクリプトで手組みする。
- **`.icns` の形式が現行 Mac と違う**。現行の `iconutil` が作る `.icns` は
  PNG ベースの新しいアイコンタイプ（`ic07`/`ic08`/…、256・512・1024px）で、
  Tiger の Finder はこれを解釈できず**アイコンが真っ白**になる。Tiger が
  読めるのは「クラシック」タイプ（`is32`/`il32`/`ih32`/`it32` ＋ 8bit マスク、
  16〜128px、非圧縮または PackBits）だけ。libicns の `png2icns` で
  `png2icns out.icns 16.png 32.png 48.png 128.png` と作れば正しく出る。

## 5. 起動経路の罠

- **実行ファイルをパスで直接 exec すると GUI セッションに登録されない**。
  SSH 越しはもちろん、実機の Terminal から
  `TigerQuickLook.app/Contents/MacOS/TigerQuickLook` と叩いても、
  LaunchServices を通らないので `LSUIElement` が適用されず、
  **メニューバー項目・Finder への AppleScript・プレビューウィンドウが
  すべて無反応**になる。しかも `CGEventTap` だけは低レベルなので動いてしまい、
  「タップは張れているのに何も起きない」という切り分けづらい状態になった。
  → 必ず `open App.app` かダブルクリック、ログイン項目から起動する。
- **この実機の `open` は `--args` を知らない**（バージョンが古い）。
  引数を渡したいときは `open -a App.app file` の形にする。
- **AppKit が直接 exec 時の引数を `application:openFile:` に流し込む**ことが
  あり、`--agent` が「開くべきファイル」として渡ってきて単発モードに落ちた。
  対策として、`-` 始まり・非実在パスを弾き、`--agent` 明示時はグローバル
  フラグでエージェントモードを強制、`applicationDidFinishLaunching:` でも
  「実在するファイルが渡されたときだけ単発モード」に絞った。

## 6. 実機ビルドのワークフロー

`ppc_claude_cli`（同じ iBook 上で動く Perl 製エージェント）で確立した方法を
流用した。

- ソースは現行 Mac で編集し、`scp` で iBook に転送。
- **ビルドは iBook 実機の上で行う**（クロスコンパイルしない。実機の PowerPC
  gcc で本当にビルドする）。
- **画面の確認は実機を直接見る**。SSH 越しのプロセスは WindowServer に
  繋がらず、`screencapture` もこちらからは動かせない。ビルドと CLI レベルの
  動作確認は `ssh` で回し、見た目は実機の画面で確認、という分担。

---

## 工夫した点（まとめ）

- **単一バイナリ 2 モード**：引数にファイル → 単発プレビュー（使い捨て）、
  引数なし → 常駐エージェント。ログイン項目にはアプリ本体をそのまま登録
  できる。
- **タップの状態を前面アプリに追従**させ、日本語入力との衝突を回避（上記 3）。
- **タップが高負荷で無効化されたら**（`kCGEventTapDisabledByTimeout`）
  自動で貼り直す。
- **プレビューを閉じたらフォーカスを Finder に返す**
  （`-[NSWorkspace launchApplication:@"Finder"]`）。
- **メニューバーに「QL」ステータス項目**を置き、常駐していることが分かる／
  そこから終了できるようにした。
- 対応形式・機能を絞り、**「やらない」判断を明文化**して、非力な実機での
  軽快さを守った。

## v0.2：対応形式の拡張（追加ライブラリなし）

「レイアウト再現」は捨て、「タイトルだけでは思い出せないファイルの中身確認」
に目的を絞ったので、外部ライブラリを足さずに Tiger 同梱ツールだけで広げられた。

- **画像**：`tiff/tif/gif/bmp` を追加。ImageIO がそのまま扱う（分岐に足すだけ）。
- **プレーンテキスト全般**：`.md` はじめ `.csv/.json/.xml/.log` や各種ソース
  拡張子を広く許可。さらに **拡張子が無い/未知でも、先頭 8KB を覗いて
  「NUL なし・制御文字 3% 未満」ならテキスト**として表示する
  （`TQLLooksLikeText`）。「明らかにテキストなのに無反応」への対処。
- **旧 Word `.doc`（Office 2004 世代の BIFF/OLE）／RTF／HTML**：
  **Tiger には `/usr/bin/textutil` がある**。`textutil -convert txt -stdout --
  file.doc` で本文が取れる（実機で日本語込み確認済み）。antiword/catdoc の
  バンドルは不要だった。
- **`.docx/.pptx/.xlsx/.odt/.ods/.odp`**：中身は ZIP。**Tiger の
  `/usr/bin/unzip`（Info-ZIP 5.51）** で本文 XML だけ取り出す：
  - docx → `word/document.xml`
  - pptx → `ppt/slides/slide*.xml`（unzip 自身のワイルドカード照合）
  - xlsx → `xl/sharedStrings.xml`（セルの文字列。識別には十分）
  - ODF 各種 → `content.xml`
  取り出した XML はタグを機械的に剥がす（`</w:p>` 等を改行に、`<...>` を除去、
  主要な実体参照だけ復元）。`NSRegularExpression` は 10.7 以降なので使わず素朴に走査。

### v0.2 で踏んだ Tiger SDK の差分

- **`NSUInteger` / `NSInteger` が無い**（`CGFloat` と同じく 10.5 から）。
  長さ・添字は `unsigned` を使う（10.4 の `-[NSString length]` も `unsigned int`）。
- **`-[NSString stringByReplacingOccurrencesOfString:withString:]` が無い**
  （10.5 から）。`NSMutableString` の
  `replaceOccurrencesOfString:withString:options:range:`（10.0〜）で代用。
- 外部コマンドは `NSTask`＋`NSPipe`。stderr は `fileHandleWithNullDevice` に
  捨て、stdout はチャンク読みして上限で `terminate`。例外は `NS_DURING`/
  `NS_HANDLER`（`@try` は書けるが当時の作法に合わせる）。

## v0.3：プレビューウィンドウを使い回す

v0.2 の矢印キー移動は、各 `build*Window...` が毎回 `_window` を release して
新しい `NSWindow` を作っていたため、1 枚進むごとに画面が一瞬消えて再センタリング
されていた（非力なマシンではラグも増幅）。

- `-installContentView:size:title:` を新設。`_window == nil` のときだけ
  `NSWindow` を作り、以降は **`setContentView:` で中身を差し替え、
  `setContentSize:` でサイズを合わせ、`setFrameTopLeftPoint:` で左上を固定**する
  だけ。`build*` メソッドは release/makeWindow/setContentView の 3 手を
  この 1 呼び出しに置き換えた。
- `-showPreviewForPath:` を「新規プレビュー（毎回センタリング）」と
  `-showPreviewForPath:keepingPlacement:`（矢印移動、位置維持）に分割。
  v0.2 で入れた `_preferredTopLeft` / `_hasPreferredTopLeft` の当て木は撤去。
- 毎回の `orderOut:` もやめた。ウィンドウは出したまま中身だけ変わる。
- 画像のデコード自体のコストは残る（新しい画像を読むので当然）。減ったのは
  ウィンドウ再生成ぶん。

## v0.4：矢印ナビの「詰まり」と、表示文字列の英日併記

**詰まり**：矢印で隣が xlsx 等の「拡張子は対応だが本文を取り出せなかった」
ファイルだと、そこで `showPreviewForPath:` が何もせず返り、前のプレビューが
出たまま `_currentPath` も動かない。次の矢印も同じファイルに当たって進めず、
しかも画面は前のファイルなので誤解しやすい。

- `-showPreviewForPath:keepingPlacement:` を **BOOL 返り** に変更（実際に
  表示できたら YES）。
- `-doStepPreviewBy:` は delta 方向へ進みながら、表示できるまで次々試す
  （上限 40 件）。全滅／端に達したら `NSBeep()`。
- 再入ガード `_stepping`：office 展開の `waitUntilExit` が runloop を回すため、
  キー押しっぱなしで `stepPreviewBy:` が入れ子で呼ばれうる。`stepPreviewBy:`
  を薄いラッパーにして `_stepping` を立ててから `doStepPreviewBy:` を呼ぶ。

**英日併記**：アプリが画面に出す文字列は約 6 か所だけ（メニューバーの
ツールチップ、無効化されたヒント行、Quit、「補助装置にアクセス」OFF の
ダイアログ、イベントタップ失敗ダイアログ、テキスト読み込み失敗の 1 行）。
翻訳の仕組みは持たず、各文字列を英語ブロック → 区切り → 日本語ブロック の
併記にした。1 バイナリで英語圏・日本の両方が読める。非 ASCII を含むので
`J()`（= `stringWithUTF8String:`、GCC 4.0 の `@"..."` 文字化け回避）を復活。

## v0.5：前面アプリの切り替えをポーリングではなく即時通知で拾う

きっかけは MacRumors の書き込み。「10.4 に通知が無いと言うが、LaunchServices は
どこかで今の前面アプリを追跡してるはずだから、AppKit/LaunchServices/
CoreGraphics のプライベート API を覗いてみては」という指摘。

調べたら、プライベート API を漁るまでもなく **Carbon Event Manager に
そのものずばりの公開イベントがあった**。

- **`kEventClassApplication` / `kEventAppFrontSwitched`** — 前面アプリが
  変わるたびに「登録している全ハンドラに」飛んでくる Carbon Event。
  ヘッダのコメントに `Availability: Mac OS X 10.0 and later` とあり、
  権限に関する注記も無い。
- 紛らわしいのが **`GetEventMonitorTarget()`**（10.3〜、生の
  `kEventRawKeyDown`等をプロセス横断で監視できる仕組み）で、こちらは
  ヘッダに「`RawKeyDown`/`RawKeyUp`/`RawKeyRepeat` の監視には
  『補助装置にアクセスできるようにする』が要る」と明記されている。
  `kEventAppFrontSwitched` はこれとは別物で、権限は要らない。

**実機で検証**：`InstallApplicationEventHandler` で
`{kEventClassApplication, kEventAppFrontSwitched}` を購読するだけの
最小 Cocoa+Carbon アプリ（`NSApplication` の run loop の上で動かす）を作り、
`open` で起動して `osascript` で Finder ⇄ TextEdit を切り替えたところ、
**遅延なく確実に発火**（`FrontSwitched -> Finder` 等、ログをファイルに
直接書いて確認。NSLog は当日 syslog に出なかったため）。

**実装**：`enterAgentMode` で `InstallApplicationEventHandler` を張り、
コールバックから既存の `pollFrontApp:`（Finder最前面判定＋`CGEventTapEnable`
の有効/無効切り替え）をそのまま呼ぶだけ。ロジックは変えず、「いつ呼ぶか」を
0.3秒ポーリングからイベント駆動に変えただけなので改修は小さい。取りこぼし
対策として、ポーリング自体は間隔を 2 秒に伸ばして保険で残した
（`dealloc`で`RemoveEventHandler`の後始末も追加）。

結果、README に書いていた「Finderに切り替えた直後の約0.3秒は Space が
効かないことがある」という制限がほぼ解消された。`build.sh`に
`-framework Carbon`を追加。

## v0.5 実機テストで判明したこと

- **矢印移動時、Finder のハイライトが追従しない。** 見た目上どのファイルを
  表示中か分かりにくいという指摘。`-syncFinderSelectionToPath:` を追加し、
  移動が成功するたびに `tell application "Finder" to set selection to {...}`
  を投げてハイライトを追従させるようにした。既存の選択取得用
  `NSAppleScript`(`_selectionScript`)とは別に、パスを都度埋め込んだ
  スクリプトをその場でコンパイル・実行する(パスは`\`と`"`をエスケープ)。
- **メニューにバージョン番号を表示。** 「実は古いビルドのままだった」を
  この プロジェクトで何度も踏んだので、`CFBundleShortVersionString` を
  「QL」メニューの先頭に出すようにした(実際、この機能を追加した直後の
  テストでユーザーが見ていたのは Info.plist をまだ 0.4 のまま上げていな
  かっただけで「古いビルド」ではなかった — バージョン番号の更新はリリース
  作業の一部としてまとめて行う運用なので、開発中は表示と実体がズレうる
  ことに注意)。
- **アイコン表示で「隣に見えるファイルと違うところへ飛ぶ」現象。**
  ユーザー自身が原因を特定：矢印移動は `NSFileManager` でディレクトリを
  読んで**ファイル名でソートした自前のリスト**を辿っているだけで、Finder
  ウィンドウの**画面上の配置**（アイコン表示で「名前」以外に整列・手動配置
  している場合の見た目の並び）は見ていない。Finder を「名前」で整頓する、
  またはリスト表示にする（常に名前順）と、画面の並びと一致して問題が消える
  ことを実機で確認。
  - ついでにソートを `localizedCaseInsensitiveCompare:` から
    `NSNumericSearch` 付きの比較(`TQLCompareFilenames`、
    `sortUsingFunction:context:`)に変更。`2.jpg` が `10.jpg` より前に来る
    ようになり、Finder の「名前」整頓により近づいた（10.4 の
    `NSNumericSearch` は 10.2 から存在、SDK ヘッダで確認済み）。
  - 画面上のアイコン配置そのものに追従する機能(Finder に位置を問い合わせて
    行/列で並べ直す等)は複雑になりすぎるため見送り。README/同梱readmeに
    「名前順で整頓するかリスト表示にすれば一致する」と明記して対処。

さらに実機テストで、この限界が「↑/↓ が ←/→ と全く同じ(どちらも単に
「リストの1つ前/次」)」という形でも表面化した。フォルダの隅で「←」が
上の行末に回り込むのは実は正しい読み順の挙動だが、「↑」を押しても
「画面上で真上のアイコン」には行かない(単にリストの1つ前へ行くだけ)ため、
途中に非対応ファイルが挟まると特に列がズレて見える。

**本当に直すには**：Finder に `position of every item of window 1` で
画面座標を問い合わせ、Y座標でグルーピングして行を作り、行内はX座標で
並べ、上下移動は「別の行のうち最もX座標が近いアイテム」を探す、という
2次元グリッドを自前で組み立てる必要がある。どのウィンドウを見るかの曖昧さ
(複数Finderウィンドウ)、大きいフォルダでの座標取得コスト、Apple Event の
リスト構造(名前と座標の2本の並行リスト)を初めて自力でパースする必要が
あることなど、見た目以上に工数とリスクが大きい。v0.5 では見送り、
List表示 or 「名前」整頓での利用を案内するに留めた(ユーザーとの合意)。
本格的なグリッドナビは将来のバージョンの独立した検討課題として残す。

## v0.6：デスクトップでプレビューを閉じると Finder ウィンドウが勝手に開くバグ

実機での日常使用で発見。デスクトップに並べたスクリーンショットを Space で
見て、もう一度 Space で閉じると、**必ず**新しい Finder ウィンドウ（起動
ディスクのルート）が開いてしまう。ダウンロードやピクチャーのようにフォルダを
ウィンドウで開いて見ているときは起きない。

**原因**：フォーカス返却に使っていた `-[NSWorkspace launchApplication:@"Finder"]`
が、Dock アイコンをクリックしたときと同じ経路を通るらしく、対象アプリが
**ウィンドウを1枚も開いていない状態**だと「新規ウィンドウを開く」動作を
誘発する。デスクトップを見ているだけの状態は、Finder にとって「開いている
書類ウィンドウが0枚」の状態そのもの（デスクトップのアイコンは背景描画で
あって書類ウィンドウではない）。開くウィンドウの中身が「起動ディスクの
ルート」なのは、Finder 環境設定の「新規 Finder ウインドウで開くもの」の
既定値がそれだから。ダウンロード/ピクチャーは実際にウィンドウが開いている
ので、この誘発が起きず、ただ前面に戻るだけで済んでいた。

**修正**：Carbon の `SetFrontProcess`(プロセスを前面にするだけで、
「開き直し」のような副作用を持たない)に切り替えた。Finder の
`ProcessSerialNumber` は `GetNextProcess` で全プロセスを走査し、
`CopyProcessName` が返す名前が `"Finder"`(日本語環境でもローカライズされず
そのまま)のものを探す。見つからない/`SetFrontProcess`が失敗した場合のみ、
元の `launchApplication:` にフォールバックする。

以前から `-[NSWorkspace launchApplication:@"Finder"]` は「本当にこれで
十分か」という保留事項として残していたが、実機の日常使用で初めて実害が
出た形。GUIの副作用は、こうして実際に使い込まないと見えてこないことが
多い。
